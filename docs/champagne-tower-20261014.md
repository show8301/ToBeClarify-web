# 香檳塔功能盤點與贈送、分潤規則

日期：2026-10-14。盤點基準：Web `c8a4ad7`、API `1d2aeba` 的本機 checkout；本文件不代表正式環境已部署本次修改。

## 原有實作

| 環節 | 本次修改前的程式行為 |
| --- | --- |
| 菜單設定 | 「香檳塔事件」寫入 `policy.eventCategories` 的 `champagne_tower`；不以名稱、標籤或菜單分類猜測 |
| 套餐 | 自身與所有子品的事件分類聯集；只要其中一個子品標記，整組便能觸發香檳塔通知 |
| 報價與下單 | 保存名稱、價格、數量、分類與套餐內容快照；商品改名或重新分類不改寫歷史 |
| 通知 | 提交成功的交易內建立 outbox；香檳塔與一般點餐／指名的命中規則合併為同單同收件人的通知；是否啟用、受眾、優先級、音效及重複提醒依通知規則決定 |
| 接單 | 標記分類本身不要求人工接受；沿用一般餐點／協調接單流程；通知已讀或「已知道」不等於接單 |
| 信物 | 香檳塔仍算一般餐點，能使用餐點信物折抵 |
| 歸屬 | 餐點請求只含商品、類型與份數，沒有受贈店員；同單指名店員不會自動取得餐點分潤 |
| 結算 | 餐點收入進共同營收；一般日依服務／經理池、幕後池及公司比例分配；活動日依活動工時分配 |

因此，原有「香檳塔事件」是訂單事件辨識能力，尚不是完整的贈送與分潤功能。小費雖已有指定店員及比例欄位，但香檳塔不能另建一筆小費代替，否則會重複收款或失去商品履約、取消及快照關聯。

## 本次確認的規則

1. 香檳塔不可使用餐點信物折抵。
2. 每一筆香檳塔商品列可選一位有效店員，或不指定店員、送給店家。預設送給店家；同款商品給不同店員時分成不同列。
3. 指定店員的比例沿用該營業日結算規則版本的 `designatedSharePercentage`，不讓顧客調整比例。
4. 店員香檳塔分潤獨立列為「香檳塔受贈分潤」，額外加到薪資，不被既有「時薪與指名服務分潤擇高」吸收。
5. 指定店員後的店家剩餘額進共同營收；未指定時全額進共同營收，不是公司獨占全部收入。
6. 活動日也先保留指定店員分潤，再將剩餘額放進活動池、扣除活動費用並按活動工時分配。受贈店員仍可依原有活動工時規則取得自己的活動分配。
7. 贈送對象與陪伴／服務指名分開，不收基礎指名費，不占用服務時段，也不要求先有服務指名。可贈送給有效但非當班店員。

例：若本營業日指名比例為 70%，香檳塔商品淨收入 1,000 G，指定店員取得額外分潤 700 G，剩餘 300 G 進共同／活動池。若送給店家，1,000 G 全部進共同／活動池。70% 是範例，不是本次另行設定的新比例。

## 套餐、取消與結算邊界

- 套餐自身標記或從子品繼承香檳塔時，以整組套餐為一筆商品：整組不可折抵，整組只有一位贈送對象，整組收入依相同比例分潤。現有套餐沒有可供拆分的子品成交價，不自行猜測拆價。
- 一般餐點與香檳塔混單時，信物只分配給一般餐點；不把一般餐點折抵按全單比例攤到香檳塔或指名服務。
- 香檳塔分項取消使用既有履約取消金額，取消部分不再計分潤，也不退回餐點信物；未取消部分依原比例計算。取消／拒絕／過期整單不進結算來源。
- 管理者對整單的金額折讓仍按可收取的淨額比例分配；香檳塔不可折抵信物，不代表不能有店內帳務折讓。
- 有現場帳款時，既有「實收減實退、扣除保留款」的比例縮放繼續作用於香檳塔分潤；活動池先扣掉受贈分潤，固定活動費用只扣一次。
- 尚未解決的帳款歸屬與保留款依既有未決／結算政策處理。本次沒有建立新的收款、退款或現金紀錄。
- 新欄位只記錄新訂單的分類與受贈快照；歷史資料預設維持原帳務，不依當前菜單分類或同單指名推測受贈者，不追溯改算已完成結算。
- 本次沒有增加提交後直接改贈送對象的入口；需要更正時，使用既有取消、重新下單及結算更正流程，保留紀錄。

## 程式與契約

- [菜單設定說明](../features/admin/menu/MenuPolicyEditors.tsx)、[顧客餐點頁](../features/ordering/components/MealOrderPage.tsx)、[代客點餐](../features/admin/orders/AdminAssistedOrderPanel.jsx)、[工作台點餐](../features/admin/operations/WorkbenchOrderComposer.tsx)、[訂單品項](../features/admin/orders/AdminOrderItemRow.tsx)、[通知訂單明細](../features/admin/notifications/NotificationOrderPage.tsx)及[正式報價](../features/ordering/components/OrderQuoteReview.tsx)顯示贈送對象。
- API `MenuDto.champagnePolicyVersion=1` 宣告新能力，Web 只在此能力存在時提供贈送選擇及不可折抵的本地估算，正式金額仍以 API 報價為準。
- `meals[].recipientStaffId` 為可選欄位；API 拒絕一般餐點指定受贈者及無效／停用店員。提交交易重新確認商品政策及受贈店員，報價綁定受贈對象。
- 訂單品項新增 `isChampagneTower`、`recipientStaffId`、`recipientStaffName`；菜單訂單快照同步保存受贈資訊。後續改名不覆寫快照。
- 通知摘要與履約名稱顯示受贈對象；原通知的規則受眾、合併及接單語意不因受贈對象改變。香檳塔贈送不會觸發「服務指名」規則。
- [資料庫 migration](../../ToBeClarify-api/db/migrations/20261014_01_champagne_recipients.sql)只新增三個訂單品項欄位，沒有正式資料回填。
- 客戶餐點頁抽成新 TSX 元件。既有 `OrderClient.jsx` 與 `AdminAssistedOrderPanel.jsx` 保留原檔格式，局部修改串接，避免把其餘指名、包廂與小費流程納入本次全面遷移；剩餘 JSX 尚不具完整 strict 型別檢查。

## 驗證與發布狀態

Web production build、TypeScript 與本次 TS/TSX 靜態分析已通過；既有 JSX 檔受目前 lint 設定排除，新餐點頁有沿用圖片顯示方式的 `no-img-element` 提示。API Release build 已通過。

[獨立金額回歸檢查](../../ToBeClarify-api/tests/ChampagneAccounting/Program.cs)透過實際結算計算器核對：店家共同池、混單信物、兩位受贈者、部分／全部取消後來源金額、折讓、額外薪資、活動日不重複分配及現場淨實收。使用記憶體來源資料，沒有資料庫連線或真實交易；不等於已驗證 SQL migration、持久化或完整下單流程。這個手動檢查專案未接入 `dev` 部署工作流程。

手動執行：API 目錄 `dotnet run --project tests/ChampagneAccounting/ChampagneAccounting.csproj --configuration Release`，使用專案要求的 .NET 10 SDK。

仍需整合驗收：套餐繼承與整組不可折抵、無效受贈者拒絕、變更贈送對象後重新報價、同一 quote token 重送、實際分項取消的信物／金額回傳及通知合併。未啟動本機預覽，尚未核對實際渲染與字型。

本次尚未套用任何環境的 migration、部署 API 或推送 Web。發布時先備份並套用 migration，再依 API 正常 `main` 發布流程交付；Web 先到 `dev`，使用者確認後才以 `dev` → `main` 手動晉升。
