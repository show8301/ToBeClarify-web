# 指名可預約時段修正

## 範圍

- Web：`codex/fix-nomination-availability`，從當時的遠端 `dev` 建立。
- API：同名分支，從當時的遠端 `main` 建立。
- 不修改出勤事件、歷史訂單或薪資，不需要 DB migration／新設定。
- 沿用點餐頁版型、色彩、指名方式及金額計算。原 `OrderClient.jsx` 只做元件串接；實質修改的指名頁拆成 `NominationPage.tsx`，避免整份既有點餐流程同時遷移型別。

## 顧客操作

1. 保留班前預約，但只能預約核准班次內、足以容納服務加緩衝時間的空檔。
2. 用既有同源 ordering client 取得 `nomination-availability`；30 秒、返回頁面及手動重新確認時更新。切換 token／營業日或失敗時，不沿用另一份資料宣布可預約。請求有取消及逾時清理。
3. 開始時間由自由輸入改成有效時段下拉選單，維持分鐘精度、以台灣時區顯示；更換服務／節數重新計算。原選時段失效時提示重選，不偷偷替換顧客已選時間。
4. 已滿、未到班、暫停接單及服務中不再混用「可指名」。正常關店前已滿、但班內仍有關店後空檔時，另標示需店家確認。
5. 公開店員卡片透過既有狀態更新讀取新增 `nominationStatus`，「可以指名」篩選依正常時段仍有空檔判斷，不再只看長期資格。舊 API 尚無欄位時，只稱「開放指名」（資格），不宣稱目前有空；原 `isNominatable` 相容契約不改。
6. 客戶端的空檔只是讀取當下資訊，送單／接受／開始的最終資格仍由 API 在交易內判斷；購物車不會保留時段。尚未承接請求不預占，兩筆重疊請求不能同時成立。

## 後台

- 「立即開始」預覽提供 `startBlockedReason`，顯示尚未到班、班次外、預約重疊或仍有服務中的原因，並停用確認按鈕。
- 即使預覽通過，操作時仍由 API 重驗。不可因已打卡就提前開始服務，不把超時未完成服務當成可接新單。
- 保留關店後協調，以及把尚未成立的衝突請求交回協調的流程；不以立即開始挪走已成立預約。

## 驗證與限制

建置／靜態檢查與實際營運驗收分開。未用正式資料建立測試訂單、打卡或改動班表；未宣稱 DB 交易及手機畫面已完成人工驗收。

新增純邏輯回歸案例供明確要求時或人工執行，不加入 dev 部署必要關卡：

- Web：`node --experimental-strip-types --test tests/nomination-availability.test.mjs`。
- API：在 API 專案執行 `dotnet run --project tests/NominationAvailability/NominationAvailability.csproj`；只呼叫純時段政策，不連 DB／HTTP。

人工驗收清單（不是已執行紀錄）：

| 情境 | 預期 |
| --- | --- |
| 班次 20:00 開始，19:30 已打卡 | 未到班；可預約 20:00 後空檔，不可立即開始服務 |
| 已有 21:00–22:00 占用 | 含服務及緩衝時間不能與該區間重疊；相鄰邊界允許 |
| 預約至閉店、沒有正常空檔 | 顯示今日預約已滿；若班內仍有關店後空檔須明確標示協調 |
| 跨午夜班次 20:00–02:00 | 01:00 屬原營業日；不得把服務／緩衝排到 02:00 之後 |
| 服務預定結束已過但尚未完成 | 不宣告空閒，不開新預約空檔；完成後重讀再開放 |
| 兩客人同時選同一空檔 | 寫入／接受時重新核對，不可同時成立重疊指名 |
| 預覽後他人改班或承接 | 操作被 API 拒絕，提示重新確認；不繞過錯誤 |
| 停止接受新指名 | 不收新單，但不取消既有預約；有效既有服務仍能開始 |
| 時段 API 失敗、缺欄或營業日不符 | 不提供新增指名，不用靜態卡片狀態代替 |

## 發布

API 新增端點與欄位對既有 Web 相容；先發布 API，再把 Web 合到 `dev` 驗收。API 沒有獨立測試主機，API `main` 就是正式發布，必須另取得發布授權。Web 確認後依 `dev → main` 人工 PR 推進。本次開發本身不代表已取得推送或發布授權。
