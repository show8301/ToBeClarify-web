# 服務員工作台：收款流程方案與篩選盤點

日期：2026-10-18。依本地來源碼盤點；未對正式資料庫逐筆查帳。已實作三處說明浮層、顧客搜尋選單、搜尋欄外觀，以及使用者後續選定的服務與收款並列介面。以下交易整合與獨立待收清單仍為提案。

## 使用者選定：僅整合畫面、兩項工作獨立送出

- 服務員工作台的現場待辦與顧客訂單均由「服務處理／收款」開啟同一個目前處理面板；桌面左右並列，1100px 以下上下排列。
- 左側直接沿用 `OrderFulfillmentPanel` 的接單、開始、完成及其他原有操作；右側共用原有同單收款表單、金額核對、帳款版本及 operation ID。
- 兩區獨立送出，各自讀取及顯示進度／錯誤，不要求一起成功，也不自動由服務完成建立實收。沿用現有 API、資料庫及權限。
- 處理面板放在篩選清單之外，以訂單 ID 維持元件實例。完成後即使離開清單或變更搜尋條件，面板也保留；跨期完成後離開來源清單時，仍以既有單筆履約與顧客帳款 API 重新核對。
- 帳款更新期間保留實收金額與備註；讀取失敗保留草稿並停用新收款。版本衝突可重新核對後送出，結果不明時只能沿用同一筆操作查回／重試。
- 收款執行中或結果不明時鎖住訂單切換及面板關閉。一般重新讀取保留輸入；操作人主動關閉或切換至另一張訂單時結束目前草稿。

此版本實作畫面並列，不包含下表 B 的原子交易命令，也不變更接單、服務完成、收款及關店的業務規則。

## 現況與漏登原因

- [服務員待辦](../features/admin/operations/serviceQueue.ts)以未完成分項、待店家承接及待協調判定，不包含獨立的帳款待收條件。[工作台](../features/admin/operations/AdminServiceWorkbench.tsx)先排除沒有服務待辦的訂單，故服務全完成後，即使未收款，也會離開這份清單。
- [同單明細](../features/admin/operations/WorkbenchGuestOrders.tsx)已分開呈現處理進度與收款狀態，但完成與收款各自開啟不同對話框。
- [完成操作](../features/admin/operations/WorkbenchItemCompletionDialog.tsx)送出分項轉移；[收款操作](../features/admin/operations/WorkbenchOrderReceiptDialog.tsx)另寫入 `cash_receipt`，附有訂單、收款營業期、版本及 operation ID。完成分項不會替代收款登記。
- API [帳款讀取](../../ToBeClarify-api/src/Repositories/Ordering/OrderingFinanceRepository.cs)以非取消／失效／拒絕訂單總額及加收、折讓計算應收，再獨立扣除實收減實退。不能把「完成服務」解讀為收到錢；目前應收計算也不是只在點擊接單確認時才納入。
- [經理帳款待辦](../features/admin/operations/ManagerFinancePanels.tsx)已有待收、待退及待核對入口。服務員現場流程缺少同等獨立、持續可見的待收清單。

## 可選介面方案

| 方案 | 操作方式 | 優點與限制 |
| --- | --- | --- |
| A：完成後接續收款 | 分項完成成功後，仍有待收時直接開啟同單收款；可選「已收到，登記實收」或「尚未收到，留待收」。 | 可沿用現有兩支 API，改動較小。兩步各自保存，須顯示「服務已完成／收款未登記」及可恢復的下一步。 |
| B：同一視窗確認服務與實收 | 同時呈現完成數量、尚欠、本次收到金額；明確選擇「完成並登記實收」或「僅完成服務」。 | 同一次確認可辦完兩件事。若要求兩件同時成功，應新增 API 組合命令，在一個交易內留下兩份獨立紀錄；瀏覽器依序呼叫兩支 API 不能保證原子性。 |
| C：獨立帳款待辦／顧客結帳 | 服務清單旁常駐待收清單，服務完成後仍保留；同顧客可逐單登記，或以對帳視窗確認分攤。 | 適合先服務後結帳、多張訂單及不同人收尾；單獨使用仍需切換入口。顧客整筆結帳若跨多張訂單，需 API 明確分攤，不能全額歸到第一張單。 |

建議先做 **A + C**：減少完成後忘記登記的機會，同時讓稍後付款及漏登款持續可見。若現場多數工作確實在交付時同時收款，再升級 B，並讓接單／開始服務時也可獨立收款，以支援先付。

### B 的具體例子

訂單尚欠 100,000 G，服務員確認餐點已送達，當下只收到 60,000 G：

1. 視窗顯示本次完成數量、應收、已收和尚欠；實收欄可輸入 60,000 G。
2. 操作人明確確認收到款項，再按「完成並登記實收 60,000 G」。不預先勾選收款確認，也不由服務數量推算實收。
3. 成功後分別顯示「餐點已送達」與「實收 60,000 G，尚欠 40,000 G」；訂單留在待收清單。
4. 未收到錢時選「僅完成服務」，保留全部尚欠。部分送達與部分付款也各自保存，不互相推導。

## 業務篩選優先順序

| 優先 | 條件 | 資料與判斷要求 |
| --- | --- | --- |
| 1 | 服務已完成仍待收、尚未收款、部分收款 | 交叉核對完整服務進度與 API 帳款；應收減淨實收大於零。不得從訂單完成狀態推算收清。 |
| 1 | 已離店仍待收 | 入場狀態與帳款交叉顯示，避免離店後不再出現在現場視野。 |
| 1 | 待退款 | 使用 API 退款與帳款結果；不能把負餘額當作已收清。 |
| 1 | 帳款待確認、未歸屬、讀取失敗 | 獨立分類並保留錯誤／重讀入口；不得算成零或已結清。 |
| 2 | 待店家承接、待接手、服務中、已完成 | 沿用 API 分項與允許操作，完整資料未到前歸為待確認。服務狀態與收款狀態各自篩選。 |
| 2 | 本期入場、跨期履約／跨期收款 | 來源營業期與實際收款營業期分開；不得把跨期款歸回舊營業日。跨期顧客不自動取得本期點餐資格。 |
| 2 | 在場、已離店／唯讀、狀態待確認 | 不把所有非 active 狀態一律算成已離店；在場也不等於本期可點餐。 |
| 3 | 顧客名稱／遊戲 ID、訂單編號、位置 | 名稱與 ID 直接用可搜尋選單；訂單／位置保留在現場待辦搜尋。 |

本次先實作資料已具備的入場狀態與營業期範圍。所有篩選預設「全部」，避免隱藏離店或跨期顧客；下拉列顯示名稱、遊戲 ID、入場狀態及營業期。改變篩選時保留已開啟的顧客明細，並提示選取顧客不在目前範圍。

帳款篩選下一階段應使用服務員有權讀取的 API 摘要，包含已完成但未收的本期訂單；不要只在目前服務待辦資料上再篩一次。跨期且服務全完成的欠款也需明確納入查詢範圍，不從既有跨期服務清單推定完整性。

## 帳務方案共通要求

- 實收只登記實際收到的金額；保留部分收、先付、後付、退款與零應收。
- 複合操作需保留服務與財務各自的權限、版本、稽核、所屬營業期與 operation ID；不把服務完成和帳務結清合成一個狀態。
- 網路中斷先查回相同操作結果，再決定重試；不能在不明結果下建立新的收款，以免重複登記。
- 舊帳若確實已收但漏登，應依實際收款時間及證據補登並留下原因；未收的列為待收／欠款。不能按服務完成狀態批次補造實收。
- 關店可提示待收與例外處理入口；是否阻擋或允許轉欠款需明確業務決策，最後仍由 API 檢核。這次不更動關店與結算規則。
